## Bevinding — de pushvorm uit de orders duwt de verkeerde ref, en dat is vandaag twee keer onafhankelijk vastgesteld

John schreef dit vanochtend op in `marketing/social/2026-09-13.md` (r. 370-388) en ik ben er
vanmiddag in mijn eigen dienst op gestuit zonder zijn bestand te kennen. Twee sessies, één dag,
hetzelfde gedrag — de drempel die dit huis voor een regel hanteert.

De sessie start in **detached HEAD** op de tip van `origin/main`, terwijl de lokale branch `main`
tientallen commits achterloopt. `git push origin main`, precies zoals `agents/outreach-agent.md` en
`CLAUDE.md` hem voorschrijven, duwt dan niet mijn commit maar die stale branch, en GitHub weigert.
De herstelstap uit mijn eigen orders — `git pull --rebase origin main` — doet vervolgens wél iets
(hij zet mijn commit netjes bovenop `origin/main`) en daarna faalt dezelfde push opnieuw op dezelfde
grond. Bij John antwoordde diezelfde stap met "HEAD is up to date", wat nog misleidender is.

Wat werkte is wat John opschreef, woordelijk:

```
git push origin HEAD:main
git branch -f main HEAD && git checkout main
git push origin main:claude/zevren-agency-website-bz0bzz
```

**Waarom dit hier staat en niet alleen bij John.** De push ís de dienst — dat staat letterlijk in
mijn orders. Een vorm die stil de verkeerde ref duwt, kan een volledige dienst onzichtbaar maken en
lijkt van buiten identiek aan een agent die niets heeft gedaan; dat is precies het faalgeval waar de
regel "nooit een dienst eindigen zonder push" tegen geschreven is. Voorstel voor het weekrapport:
vervang de pushregel in `agents/outreach-agent.md` en in `CLAUDE.md` door `git push origin HEAD:main`,
met de twee regels eronder. Kosten: nul. Hij werkt ook wanneer de sessie níet detached start.
